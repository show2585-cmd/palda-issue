T-01 · 근본 원인

기술 스택을 정하지 않고 바이브 코딩으로 쌓아 올림

높음

한 서비스인데 화면마다 스타일링, 아이콘, 색상 체계가 다릅니다. 키워드 분석은 직접 쓴 CSS로, iframe으로 불러오는 알림톡 체험은 Tailwind로 만들었습니다. 프로젝트 차원에서 "무엇으로 만든다"는 기준을 정하지 않고, 화면 단위로 AI가 만들어 준 코드를 그대로 붙여 온 흔적이 번들 곳곳에 남아 있습니다. 이 페이지의 다른 문제(T-02~T-04)도 대부분 여기서 나옵니다.

근거 1 · 같은 서비스, 다른 스택
항목메인 앱 (키워드 분석)알림톡 앱 (/crm/, iframe)
스타일링직접 쓴 CSS (BEM) + CSS ModulesTailwind CSS v4 유틸리티 669종 + palda CSS
색상 토큰--palda-* (보라 #6466fa)--palda-* + shadcn 기본 토큰 --primary, --muted-foreground, --accent: oklch(…)
회색 계열--palda-gray-* 하나palda-gray + Tailwind gray·zinc·slate·neutral 5종
아이콘인라인 SVG 30개 (선 두께 4종)lucide-react
UI 기본 부품직접 구현Radix UI (Select, Popper 등)
라우팅History API 직접 구현History API + hashchange 직접 구현 (또 다른 방식)
차트·검증Recharts, Zod없음
앱 사이 통신postMessage (palda-demo:navigate, palda-demo:crm-state)
근거 2 · 사람이 정했다면 나오기 힘든 값
  • 알림톡 앱의 글자 크기 임의값: text-[6.736px], text-[7.858px], text-[8.14px], text-[8.981px], text-[15.385px], text-[22.222px] 등 18종. 디자인 시안을 비율대로 환산한 값이 그대로 들어감
  • Tailwind 임의값([…]) 573회. 그중 bg-[#F9F9F9]와 bg-[#f9f9f9]처럼 대소문자만 다른 같은 색이 따로 존재
  • 메인 앱에도 font-size: 11.894px가 있고, 이 값은 알림톡 앱에도 똑같이 나옴. 같은 계산 결과를 양쪽에 복사한 것
  • shadcn/ui 기본 토큰(--card-foreground, --popover, --destructive …)이 palda 토큰과 나란히 정의됨. 템플릿을 그대로 가져온 뒤 정리하지 않음
근거 3 · 중복 비용
  • React 19.2.8이 두 번들에 각각 통째로 들어 있음. 알림톡 체험까지 보면 JS 합계 2.59MB (gzip 약 764KB)
  • palda 디자인 시스템 CSS가 양쪽에 복사됨: 완전히 같은 CSS 규칙 430개(약 60KB)가 두 파일에 중복
  • 같은 회사 색인데 메인 앱 hex 64종, 알림톡 앱 hex 79종이 따로 존재
영향
  • 일관성: 키워드 화면과 알림톡 화면의 버튼·회색·아이콘이 미묘하게 달라 한 제품처럼 보이지 않음 (UI/UX U-01, U-02의 원인)
  • 유지보수: 브랜드 색 하나를 바꾸려면 palda 토큰, shadcn 토큰, Tailwind 임의 hex를 모두 찾아 고쳐야 함. 새로 들어온 개발자는 "이 화면은 무엇으로 만들지"부터 판단해야 함
  • 성능: 같은 라이브러리와 CSS를 두 번 내려받음
  • 품질 관리: 기준이 없으니 코드 리뷰에서 "틀렸다"고 말할 근거도 없음. AI가 만든 코드가 그대로 쌓임
개선 방향
  • 기술 스택 문서(ADR)부터 작성: 스타일링(Tailwind냐 CSS Modules냐 하나만), 아이콘(lucide), UI 기본 부품(Radix), 라우터, 데이터 요청, 차트를 결정하고 기록
  • 디자인 토큰 단일화: --palda-*를 유일한 기준으로 두고, Tailwind를 쓴다면 @theme에 palda 토큰을 연결. Tailwind 기본 팔레트와 shadcn 기본 토큰은 제거
  • AI 코드 생성에 규칙 주입: 프로젝트 규칙 파일(CLAUDE.md, .cursorrules 등)에 스택과 토큰을 명시하고, ESLint·Stylelint로 임의값(text-[7.858px], bg-[#…])을 막아 CI에서 걸러냄
T-02

앱 전체가 JS 파일 하나로 나감 (코드 분할 없음)

높음

랜딩만 보는 사용자도 키워드 분석·상품 분석·키워드 비교·Recharts까지 전부 내려받고 파싱합니다. 알림톡 체험에 들어가면 iframe 앱 JS 1,478KB를 따로 또 받습니다.

근거
  • JS 1개 1,108KB (gzip 312KB). 동적 import() 0회, React.lazy 0회
  • 번들 안 Suspense 10회는 모두 React 내부 코드. 앱 코드에서 쓰는 곳 없음
  • Recharts(+ 내부 Redux Toolkit)가 메인 번들에 포함. 차트는 키워드·상품 화면에서만 사용
영향

빠른 회선에서는 체감이 적지만, 모바일 회선과 저사양 기기에서는 첫 화면 표시와 상호작용 가능 시점이 늦어집니다. 한 화면만 고쳐도 해시가 바뀌어 사용자는 1.1MB를 통째로 다시 받습니다.

개선 방향
  • 화면(라우트) 단위로 코드를 나눠, 사용자가 들어간 화면의 코드만 불러오기
T-03

라우터를 직접 구현함

중간

react-router 같은 라이브러리 없이 History API로 라우팅합니다. 경로가 20개 가까이 되고 플랫폼(naver/coupang)과 탭(products/related)이 중첩돼 있어 직접 관리하기엔 큽니다.

근거
  • pushState 3회, replaceState 7회, popstate 리스너 10회
  • 경로 예: /keywords/naver/related, /keywords/coupang/products, /keywords/compare, /products/coupang
  • 경로 분기를 문자열 비교로 처리: t==="/dashboard"?"/dashboard/100000001/alimtalk":e (샘플 스토어 ID 하드코딩)
개선 방향
  • React Router 또는 TanStack Router로 교체 → 중첩 라우트, 라우트별 lazy(T-02), 404 처리, 스크롤 복원을 함께 해결
  • 타입 있는 경로 파라미터(:platform, :storeId)로 하드코딩 제거
T-04

공통 컴포넌트 없이 화면마다 스타일을 새로 만듦 → 컴포넌트화 필요

중간

표, 카드, 탭처럼 여러 화면에 반복되는 UI를 공통 컴포넌트로 만들지 않고, 화면마다 새 클래스 이름(접두어)을 붙여 스타일을 다시 작성했습니다. palda- 디자인 시스템이 있는데도 화면 전용 접두어가 20여 종 생긴 이유입니다.

  • 같은 "표"가 5가지로 따로 구현됨: palda-table, trend-table(45회), kw-table-wrap, comparison-demo-table, cca-exposure-table
영향

표의 머리글 고정이나 정렬처럼 하나를 개선해도 다섯 군데를 따로 고쳐야 하고, 한 곳만 고치면 화면마다 동작이 달라집니다. 화면 수가 늘수록 CSS도 그만큼 커집니다(현재 290KB).

개선 방향
  • 반복 UI를 공통 컴포넌트로 만들기: 표(Table), 카드, 탭, 페이지네이션, 지표 카드 등을 palda 디자인 시스템 컴포넌트로 만들고 모든 화면에서 재사용
  • 화면 CSS는 배치만: 각 화면은 컴포넌트를 조합하고 간격·배치만 정하며, 색·글자·표 모양은 컴포넌트와 토큰에서만 정의
  • 컴포넌트 목록 관리: Storybook 같은 카탈로그로 이미 있는 컴포넌트를 먼저 찾아 쓰게 하고, 새로 만들 때는 리뷰를 거치게 함
  • 메인 앱과 알림톡 앱이 같은 컴포넌트 패키지를 쓰도록 연결 (T-01)
